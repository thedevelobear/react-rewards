# v3 engine benchmark

- **Date:** 2026-10-23
- **Plan:** [2026-10-22-v3-rewrite](../plans/2026-10-22-v3-rewrite.md), step 1c "Benchmark and budgets"
- **Compare with:** [2026-10-22-v2-baseline](2026-10-22-v2-baseline.md), on the same machine with the same method

## Summary
- WebGL holds the display's 120 fps for every effect up to 20000 particles. At 20000 the main thread is 35 to 48% busy, almost all of it script.
- Canvas 2D holds 120 fps up to 5000 particles, with the main thread 56 to 83% busy. At 20000 it falls to 40 to 65 fps, and the main thread is 96 to 98% busy. The fallback gets no particle cap ([ADR 0050](../decisions/0050-no-canvas-particle-cap.md)).
- Every burst lasts its nominal time, even at 40 fps, because the engine steps by elapsed time. Below 30 fps it would play slower instead of jumping (the loop's `MAX_DT` is 1/30 s).
- Compared with v2: v2 needed 68 to 80% of the main thread for 2000 confetti or emoji, and fell to 8.5 fps with 2000 balloons, stretching a 10 s burst to 70 s. v3 on WebGL draws ten times as many, 20000, at 120 fps with 35 to 48% of the main thread. At 500, the one count both runs share, v3 uses 11 to 13% of the main thread on WebGL and 17 to 20% on Canvas 2D, for every effect. v2 used 16 to 21% for confetti and emoji, and its balloons fell to 35 fps with the main thread 95% busy.
- Style recalculation and layout are zero: the overlay is one canvas, and nothing in the DOM changes per particle.
- The particle view's accessors and the Canvas 2D renderer's drawing of off-screen particles stay as they are ([ADR 0051](../decisions/0051-no-engine-optimisations-after-benchmark.md)).
- Not measured: a machine without a usable GPU, where WebGL2 runs in software. Step 1c asks whether Canvas 2D is faster there. This machine can't answer it.

## Method
- The harness is `demo/bench/run.ts`, run with `pnpm bench` at the root ([ADR 0048](../decisions/0048-benchmark-script-in-demo.md)). It builds the library and the demo, serves the built site with Rsbuild's preview server, and drives the site's Stress test page through its controls ([demo README, Stress test](../../demo/README.md#stress-test)).
- Each burst uses the effect's defaults apart from `count`. Confetti and emoji live up to 3000 ms, balloons up to 5000 ms.
- Each combination of effect, renderer and count runs in a fresh tab, with the renderer forced through `setRenderer` ([ADR 0033](../decisions/0033-strict-public-set-renderer.md)). The tab gets a 1.5 s settle delay and a check that `requestAnimationFrame` isn't throttled, then one warm-up burst that is not recorded, then 3 recorded bursts. After the warm-up, the harness checks that the readout names the forced renderer ([ADR 0047](../decisions/0047-burst-renderer.md)). The tables show the median of the 3.
- A burst runs from the click on "Reward me", made inside a frame callback, until the readout says the burst has ended. Frame timing comes from the harness's own `requestAnimationFrame` timestamps over that window.
- Main-thread time comes from the Chrome DevTools Protocol `Performance.getMetrics`, read before and after each burst: `ScriptDuration`, `RecalcStyleDuration`, `LayoutDuration` and `TaskDuration`. "Other" is task time minus script, style and layout: mostly paint, compositing, and the Canvas 2D renderer's raster work.
- Raster and GPU work on other threads is not included.
- The page's own work is included: the readout updates four times a second while a burst runs.
- Costs are per frame. The v2 baseline gives them per v2 update instead, because v2 stepped a fixed number of times per burst. v3 steps once per frame by the elapsed time, so the two sets of per-update numbers don't compare directly. Main-thread busy, fps, p95 frame and long frames do.
- "Long frames" counts frames longer than 1.5 refresh intervals.

## Harness
`demo/bench/run.ts`, added in PR 11. To repeat the run, install Chromium once with `pnpm --filter demo exec playwright install chromium`, then run `pnpm bench` at the root, and keep the Chromium window uncovered while it runs, because macOS throttles windows that are hidden. It writes the full results to `demo/bench/results.json`, which git ignores.
